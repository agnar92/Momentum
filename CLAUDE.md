# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A simple **daily stock watchlist** published as a static site (`docs/`, GitHub Pages). Finviz does the
pre-filtering of the stock list, yfinance supplies prices, a small Python script computes a few
screening indicators, and a plain HTML/JS page lets the user browse the result. Informational only —
not investment advice.

**History (why the repo looks the way it does):** this used to be a much larger momentum-investing tool
(S&P-style Momentum Index replication for SP500/NASDAQ100/DOWJONES/WIG20/mWIG40/sWIG80, Global Equity
Momentum, Weinstein stage analysis charts, TTM Squeeze/Breakout screeners, two automatic rebalancers,
a sector "Strategia" page, a DuckDB database committed to git). At the user's explicit request all of
that was removed ("całkowicie usuwamy momentum, rebalanser itd. Robimy prosty watchlisty do
przeglądania") and replaced by the watchlist below. It all remains in git history (last full version:
the commit before "Replace momentum/rebalancer app with a Finviz watchlist") if anything is ever needed
again. The standalone Episodic Pivot helper page (`docs/ep.html`, `js/ep.js`) and the embedded TradingView widgets were removed later at the user's request ("usuń ten widget i tak samo wszystko o EP"); they are in git history.

Code comments and CLI print messages are written in Polish; keep that convention when editing existing
files (English is fine for new, unrelated code).

## Data flow (all in `watchlist.py`, run daily)

1. **`finviz.py`** — scrapes the free Finviz screener (`finviz.com/screener.ashx`, 20 rows/page, `r=` offset)
   with the filters in **`finviz_screen.json`** (`filters` = comma-separated Finviz filter codes, copy them
   from a Finviz screener URL; `max_tickers` = cap). Default (CANSLIM pre-filter, Oct 2026): `sh_price_o10,ta_sma50_pa,ta_sma200_pa,fa_epsqoq_o25,fa_salesqoq_o25,fa_epsyoy_o25,fa_roe_o15` = C (EPS and sales of the last quarter ≥ +25 % y/y) + A (EPS this year ≥ +25 %, ROE ≥ 15 % — Finviz has no 17 %, the exact ROE ≥ 17 % is checked in the app by `CANSLIM_THRESHOLDS.roe`) + trend (above SMA50/SMA200) + price > $10 ≈ 82 stocks (153 without ROE); `max_tickers` = 300. Deliberately NOT on Finviz: N (`ta_highlow52w_b0to10h`; cup/flat bases sit 10–30 % under the high, the app sorts by distance to the pivot), the 5-year EPS filter (young leaders), next-year EPS forecast (not a CANSLIM criterion). L, S, I, M are computed by the app. The RS Rating is NOT taken from this narrow list (see `rs_universe.json` below); every other rating (industry group, Acc/Dis, EPS Rating) stays relative to the CANSLIM list. It queries four views (Overview `111`,
   Valuation `121`, Financial `161` and the Custom view `152` with `c=0,1,62,69` = Analyst Recom. + Target Price, `VIEW_PARAMS`) with the same filters and merges rows by ticker, mapping columns by
   header text (`VIEW_COLUMNS`) — sector, industry, market cap, P/E, EPS this Y / next Y / past 5Y / next 5Y,
   ROE, margins, next earnings date, analyst recommendation `recom` (1 = Strong Buy … 5 = Strong Sell) and the mean target price `finviz_target`. **Finviz silently ignores unknown filter codes** (a typo widens the list
   instead of erroring), so check the stock count after editing filters. Everything Finviz gives for free
   comes from Finviz; everything else comes from yfinance.
2. **yfinance** (`download_prices`) — ~15 months of daily OHLCV (`auto_adjust=True`) in batches of 50. The
   still-open US session is dropped (`drop_incomplete_bar`) so a manual run during trading hours never
   treats an incomplete candle as "yesterday's close".
3. **`compute_metrics`** per stock:
   - `rs_score = 0.4·R3M + 0.2·R6M + 0.2·R9M + 0.2·R12M` (cumulative returns, latest quarter double
     weight — the widely used approximation of IBD's RS Rating; the exact IBD formula and universe are not
     public) and `rs_rating` 1–99 = percentile of `rs_score` among the watchlist (`add_rs_rating`, average
     rank for ties). Stocks with < 252 bars get no RS (too young for 12M). **The rating is relative to the
     already-filtered list**, not the whole market.
   - **EPS Rating and Composite** (`add_eps_rating`, after the EPS cache step in `run`; IBD's exact EPS Rating is not public): `eps_score` = weighted mean of the YoY EPS growth of the last two reported quarters (`eps_q0_yoy` 0.35, `eps_q1_yoy` 0.25, from the Yahoo EPS cache via `eps_quarters`), Finviz EPS growth this year (0.15) and past-5-year EPS growth (0.25); components are RAW percentages with no clipping (same as the returns in `rs_score` — outliers are tamed only by the percentile ranking; the user asked for this explicitly), missing components are dropped and the weights renormalised, the latest quarter is required plus at least 2 components (`eps_score`); `eps_growth_rating` = percentile of `eps_score` among the list (`percentile_rating`, shared with the RS Rating), `eps_stability` = % of the last 8 quarters (min. 4 YoY comparisons) with positive YoY EPS growth (`eps_stability`) → `eps_stability_rating` percentile, and **`eps_rating` = round(0.8·growth percentile + 0.2·stability percentile)** (`EPS_STABILITY_WEIGHT`; without a stability value = growth percentile only; IBD's real stability factor is not public — this is a simple consistency measure and many solid growers tie at 100 %); `composite_rating` = round(0.5·RS Rating + 0.5·EPS Rating) (`COMPOSITE_RS_WEIGHT`), None unless both exist. No industry-group component (IBD's real Composite also uses SMR, Acc/Dis and group strength). Ratings are relative to the already-filtered list.
   - **M and L from CANSLIM** (user: "M i L są najważniejsze"): `market_state(sp, nasdaq)` → `watchlist.json` key `market` = `{sp500, nasdaq, regime}`; per index `index_state`: close vs SMA50/SMA200, SMA50 rising, % from the 52w high, **distribution days** (`distribution_days`: last 25 sessions with a close ≥ 0.2 % down on higher volume than the day before) and `regime` — **weekly EMA10 > EMA20 of the index = `uptrend`, otherwise `correction`** (user's rule; `ema10w`, `ema20w`, `ema_gap_pct`; SMA distances and distribution days are informational only); the overall regime is the MORE SEVERE of S&P 500 and Nasdaq (`^IXIC`, downloaded non-fatally). Breadth from our own list is deliberately NOT computed: the Finviz filter already keeps only stocks above SMA50 and SMA200. `add_group_strength` (called from `build_stocks`): `industry_rating` = percentile (1–99) among Finviz industries of the mean RS Rating of the industry's stocks in the list (min. 3 members, `GROUP_MIN_MEMBERS`); `leader` = RS ≥ 80, group ≥ 60 and not more than 25 % under the 52w high. All thresholds are heuristics, not backtested. **I from CANSLIM**: Finviz custom view 152 (`c=0,1,62,69,28,29`) also returns `inst_own` (Inst Own %) and `inst_trans` (Inst Trans %, change over the last quarter); `institutional_flag` → `inst_sponsor` = own ≥ 20 % (`INST_MIN_OWN`) and trans > 0, None when unknown. Column `Instytucje` (`inst`) in the Lista / cards (the Filtry checkbox `instOnly` went away with the Ratingi tab).
   - Qullamaggie-style inputs: `adr_pct` (100·(mean(High/Low) − 1), last 20 sessions),
     `dollar_volume_avg` (mean Close·Volume, last 20 sessions), `low_ratio_{1,3,6}m` (price /
     lowest Low of the last 1/3/6 months — a plain ratio, NO "− 1": it is only used for ranking, so sorting
     descending is enough).
   - `pct_above_sma50/200` and weekly `pct_above_sma10w/40w` (own computation; the latter feed the weekly "Co robić"), `spark` (last 26 weekly closes, % vs. first).
   - **Sell climax top** (`detect_climax_top(weekly, bases)`, user: "pełna definicja na tygodniówce"; O'Neil, How to Make Money in Stocks — core criteria from the book, numeric thresholds are mine): on WEEKLY bars, in one of the last 2 weeks (`CLIMAX_RECENT_WEEKS`) ALL of: a rise ≥ 25 % in 1–3 weeks (close vs the lowest low of the 3 previous weeks, `CLIMAX_RUN_*`), the BIGGEST weekly gain of the trend (and ≥ 8 %), the WIDEST weekly range and the HIGHEST weekly volume (also ≥ 1.5× the 10-week mean) since the trend low (lowest low of the last 104 weeks, trend ≥ 8 weeks). Confirmations `climax_conf` 0–4: exhaustion gap (open above the previous week's high, `climax_gap`), close in the lower half of the week (`climax_reversal`), close ≥ 70 % above the 40-week SMA (~200 days, `climax_ext200_pct`), late stage = ≥ 3 flat/cup bases since the trend low (`climax_stage`, `climax_late`; limited by the ~3 years of history). Stored as `climax_top`, `climax_date`, `climax_runup_pct`, `climax_week_gain_pct`, `climax_vol_ratio`, … in watchlist.json and as `climax` (weekly) / `day.climax` (same dict, marker lands on the last session of that week) in charts.json. Frontend: column `Climax` (`cx`, "⚠ n/4"), red chip `⚠ Climax top`, a warning in `readinessLine`, and on the chart a red ▼ above the bar with a dashed line through the volume (`m.climax`). Heuristic, not backtested — a warning to check the chart, not a sell signal.
   - **Acc/Dis** (`accdis_score`, `add_accdis_rating`): Chaikin money-flow over the last 65 sessions (`ACCDIS_SESSIONS`; volume-weighted position of the close in the day's range, −1…+1), `accdis_rating` = percentile among the list, `accdis` letter A ≥ 80, B ≥ 60, C ≥ 40, D ≥ 20, else E (approximation of IBD's Acc/Dis Rating, whose formula is not public). Column `Acc/Dis` (`ad`) and the A/D chip over the chart.
4. **Chart data** (`build_charts`, `docs/data/charts.json`, lazily fetched by the chart modal): a shared list of the
   last 104 weeks (`weeks`), the S&P 500 (`^GSPC`, `spx`; benchmark download is non-fatal) and, per stock, weekly OHLC
   + volume (thousands) aligned to those weeks (`weekly_ohlcv`: W-FRI bars, the partial last week is dated with the
   last session) plus SMA10/SMA40 weekly (computed on the full 3-year history, then sliced) and quarterly EPS
   (`eps`: report date, EPS, YoY % = vs. the report ~1 year earlier, `None` if no/zero base, `t` = TTM = sum of the last 4 reported quarters, `None` until 4 exist; `eps_next` = upcoming
   estimate with `t` = estimate + the last 3 reported quarters; the daily arrays also carry `sma50`/`sma200`). EPS comes from Yahoo `get_earnings_dates` (reported/adjusted EPS, ~12 quarters) and is cached in
   **`docs/data/eps_cache.json`** (`update_eps_cache`, refreshed per ticker only when older than 7 days, 4 worker
   threads, 600 s budget, errors never abort the run). Price history is downloaded for `3y`.
5. Output **`docs/data/watchlist.json`** (`generated_at`, `data_as_of` = last session date, `finviz_filters`,
   `finviz_total`, `finviz_stale`, `n_stocks`, `stocks[]`). If Finviz fails or returns suspiciously few rows
   (`MIN_TICKERS`), the previous file's stock list (and its Finviz fields) is reused and `finviz_stale` is
   set; if price coverage is below `MIN_COVERAGE` (70%) nothing is written and the script exits 1.

**Two profiles / two data sets (user first asked for separate Finviz downloads — separate configs, files and profiles — and later for ONE daily refresh running both)**: `python watchlist.py` = profile `canslim` (daily, `finviz_screen.json`, writes `watchlist.json` + `charts.json` + `eps_cache.json` + `estimates.json`). `python watchlist.py --profile qm` = Qullamaggie, run in the SAME daily workflow BEFORE the CANSLIM step (user: "jeden daily refresh który pobiera CANSLIM i Qullamaggie"; with ≈ 300 stocks it takes ~2–3 min; the QM step is `continue-on-error`, so a failure keeps the previous QM files and CANSLIM still runs; `--skip-finviz` still works locally): config `finviz_screen_qm.json` = Finviz filter `cap_midover,sh_avgvol_o1000,ta_sma20_pa,ta_sma50_pa,ta_sma200_pa` (user's own screener URL: market cap ≥ $2B (Mid and up), average volume > 1M shares, price above SMA20/50/200; ≈ 300 stocks; NO fundamentals, price or volatility filters — the user's custom measures (dollar volume, exact ADR %, price / lowest low over 1/3/6 months, top X %) are NOT Finviz filters, so the app does them). ALL Finviz views (same as CANSLIM), prices from yfinance, EPS cache + EPS Rating + estimates for every stock (user: "wszystko policzone bez względu na koszty miejsca i czasu"; `eps_cache.json` / `estimates.json` are shared by both profiles, entries of the other scanner are kept for `CACHE_KEEP_DAYS` = 45 days). RS Rating / Acc/Dis / industry groups are computed on the whole Finviz list of that run (liquid, volatile stocks above SMA20/50/200 — NOT the whole market, so RS 80 here means top 20 % of that momentum-ish group), ALL stocks are saved (`min_dollar_volume_m` / `min_adr_pct` = 0 in the config = optional cut-off; the user's thresholds live in the app's Filtry, default 20 mln / ADR 4 %, so changing them to ADR 1 / 10 mln must not leave stocks without data) into **`docs/data/watchlist_qm.json`** (`profile: "qm"`), and charts are built for ALL of them (`charts_top_pct` = 100; a value < 100 restores the old union of the top X % by price/low, `qullamaggie_select`) into **`docs/data/charts_qm.json`** (one stock ≈ 20 kB). **`docs/data/rs_universe.json`** (`{as_of, n, scores}`: sorted `rs_score` of the whole wide list, written by the `qm` run): the daily CANSLIM run computes `rs_rating` as the percentile of each stock's `rs_score` in that distribution (`add_rs_rating(stocks, universe_scores)`, `load_rs_universe`, min 100 scores) = RS against the broad market (liquid stocks above SMA20/50/200, a stricter group than the whole market), while everything else stays relative to the CANSLIM list; without the file (QM never run) it falls back to the list-relative percentile. `watchlist.json` key `rs_basis` = `{source: "market"|"list", n, as_of}` is shown in the data-info line and in the L explanation (`rsBasisText`). The distribution is refreshed by the QM step of every daily run, which runs BEFORE the CANSLIM step. Frontend: `loadData` fetches both files, `mergeProfiles` tags every stock `in_cs` / `in_qm` (a ticker in both keeps the CANSLIM record), `tabUniverse` (user: "lista to pełna lista spółek + canslim, dwa skanery, nie tylko dla canslim") — Lista / Bazy / Ulubione / Pozycje / Alerty show ALL stocks (union of both scanners), the CANSLIM tab only `in_cs` (only those have the fundamentals), Qullamaggie only `in_qm`; `loadCharts` returns charts.json plus `qm` (charts_qm.json) and `chartsForTicker` picks the file that has the ticker (the files have different week/day axes, so they cannot be merged). Without `watchlist_qm.json` the Qullamaggie tab shows a link to the daily workflow. `alerts_notify.py` also reads `watchlist_qm.json`.

**Fetching and computing are two separate steps (user: "nie chcę za każdym razem zaciągać danych — zaciąganie to jedno, obliczenia to drugie")**: `python watchlist.py [--profile qm] --fetch-only` does ALL the network work (Finviz rows, yfinance prices incl. `^GSPC` / `^IXIC`, USD/PLN, the EPS cache and the analyst estimates in `docs/data/eps_cache.json` / `estimates.json`) and writes ONLY a snapshot `raw/<profile>.pkl.gz` (`save_raw` / `load_raw`, gzip pickle of `{finviz_rows, finviz_total, finviz_stale, frames (with df.attrs splits), benchmark, nasdaq, fx, fetched_at}`; `raw/` is git-ignored). `--compute-only` reads that snapshot plus the two JSON caches and computes everything else (metrics, ratings, bases, charts, `watchlist*.json`, `charts*.json`, `rs_universe.json`) WITHOUT network (tested: the network functions raise in that step; `now_utc` = the fetch time, so the result does not depend on when it is computed; output == the all-in-one run). No flag = both, as before. `--raw-dir` changes the folder. `--save-raw` (full run only) additionally writes the snapshot after the normal fetch + compute. Workflows (user: "cofnij daily refresh jak było z obliczeniami i do deploy page dodaj uruchomienie obliczeń"): **`daily_watchlist.yml` is back to ONE combined run as before** = restore the previous snapshot (continue-on-error) → `python watchlist.py --profile qm --save-raw` (continue-on-error) → `python watchlist.py --save-raw` → publish the snapshot (force-pushed single commit on the branch `raw-data`) → alerts → commit `docs/data/` → Pages; **`deploy.yml`** ("Deploy Pages (z obliczeniami, bez pobierania danych)", on every push to `main` and manually) checks out `raw-data` into `raw/` and, when it exists, RUNS THE COMPUTATIONS before publishing: `--profile qm --compute-only`, then `--compute-only` (both `continue-on-error`, so a failed computation leaves the committed data), commits changed `docs/data/` with `chore: recompute watchlist [skip ci]` (retry loop, no deploy loop thanks to `[skip ci]`; needs `contents: write`) and uploads `docs/` — so a merged change to watchlist.py shows up on the page without any manual run; without the snapshot (before the first daily run) it is a plain deploy. **`recompute_watchlist.yml`** ("Recompute Watchlist", manual) does the same compute-only without relying on a push (kept as a manual button).

Run it: `python watchlist.py` (`--skip-finviz` reuses the previous list and only refreshes prices;
`--max-tickers N`; `--output PATH`). No database — every run recomputes from scratch.

## CI (`.github/workflows/`)

- **`daily_watchlist.yml`** — runs `python watchlist.py --profile qm` (continue-on-error) and then `python watchlist.py` every Tuesday–Saturday at 05:30 UTC (morning in Poland, after
  the previous US session closed, so the data is "yesterday's close for today's open") and on
  `workflow_dispatch` (**manual refresh**: Actions → "Daily Watchlist Refresh" → Run workflow; the page's
  "🔄 Odśwież dane" button links there). It commits `docs/data/` back (rebasing onto the current `origin/main`
  first, `git reset --mixed`, with a retry loop; commit message ends in `[skip ci]`) and deploys `docs/` to
  Pages. Finviz may block datacenter IPs — in that case the previous list is reused (see above), and the page
  shows a warning when `finviz_stale` is true. **Never use "Re-run jobs" on an old run once `main` moved on**
  (GitHub re-runs against the original trigger SHA, i.e. old code); trigger a fresh `workflow_dispatch`.
  After the data refresh an optional step runs **`alerts_notify.py`** (needs the repo secret `GIST_TOKEN` = a token with the `gist` scope, the same kind as the sync token; without it the step does nothing; `continue-on-error`): it reads the annotations from the sync gist, computes every alert line's value on the last session (`line_value_at` = Python port of `lineValueAt`, parity-tested) and, for NEW breaches (not acknowledged with OK in the app and not reported before), posts a comment mentioning the repo owner in the Issue "🔔 Alerty Watchlist" (GitHub then sends e-mail / GitHub Mobile push). "Already reported" ids live in a hidden `<!-- alert-state: … -->` comment in the issue body; an alert that stops being breached drops out and can notify again. Workflow permissions include `issues: write`.
- **`recompute_watchlist.yml`** — manual (`workflow_dispatch`): compute-only from the last raw snapshot (branch `raw-data`), no downloading; see the fetch / compute split in the data-flow section.
- **`deploy.yml`** — Pages deploy of `docs/` on every push to `main` (and manually) that first recomputes the data from the last raw snapshot (`--compute-only`, no data fetch); see the data-flow section.
- **`tests.yml`** — `ruff` + `pytest` (Python) and ESLint + `node --test` (JS) on pushes/PRs.

## Flags / consolidation (heuristic)

`detect_consolidation(ohlc, cfg)` (watchlist.py; `DAILY_FLAG` for the daily chart and `tl_*` fields, `WEEKLY_FLAG` for the
weekly chart) replaced the old "longest line through any two swings" logic that drew wrong lines. It only reports a
pattern, and only draws lines over the consolidation itself:
- **flaga**: pole (low → swing high within `pole_lookback` = 20 sessions, gain ≥ 20 %, ≥ 3 sessions long), then a
  consolidation of 7–30 sessions no deeper than 20 % (and ≤ 60 % of the pole gain);
- **korytarz**: no pole, but a tight (≤ 12 %) range of ≥ 12 sessions;
- resistance = longest line through swing highs of the consolidation that no bar pierces by > 1.5 % (slope ≤ +0.15 %/bar);
  support = same through lows but required to be roughly parallel (±0.3 %/bar), omitted when none fits;
- the last `recent` (5 daily / 2 weekly) bars may already be the breakout. **O'Neil's rule (user: "musi się zamknąć ponad linią z wolumenem, dzienna czy tygodniowa świeca; przebicie high nie jest wybiciem")**: only a CLOSE above the resistance counts, never a high, and it must come on volume ≥ 1.5× the average of the previous bars (`TL_VOLUME_MULT`; `volume_ratio`, average over `cfg["vol_avg"]` = 50 sessions daily / 10 weeks weekly) AND price must still be above the line now. `state` = "wybicie" (close above the line on volume, `breakout.confirmed` True, the first such bar is the breakout day) / "bez wolumenu" (closed above but no volume bar ≥ 1.5×: NOT a breakout, `confirmed` False) / "przy oporze" (≤ 3 % below) / None (inside, or the breakout fell back under the line); `breakout` = {date, `vol_ratio`, `confirmed`}; `info` = pole gain/dates, length, depth, `vol_ratio` (flag volume / pole volume, ≤ 0.8 = drying up).
- The same rule for **pivots** (`detect_level_break(ohlc, level, recent, avg_bars, tf)`: closes in the last 5 sessions (daily) or 2 weeks (weekly) above the open base's pivot, still above it, volume ≥ 1.5×) → `pivot_state` ("wybicie" / "bez wolumenu" / None), `pivot_vol_ratio`, `pivot_break_date`, `pivot_tf` ("D"/"W"), and for the weekly flag/box `tlw_*` (same fields as `tl_*`, from `WEEKLY_FLAG`). `vol_surge_5d` = best volume ratio of the last 5 sessions (used for the user's own alert lines: a triggered "above" line is a fresh breakout only if `vol_surge_5d` ≥ 1.5 — approximation, the exact breach day is not stored; unknown volume in an older watchlist.json keeps the old behaviour). `breakoutInfo` (Wybicia tab) therefore ranks confirmed closes-on-volume as rank 0, unconfirmed closes (reason text "… bez wolumenu — niepotwierdzone") only as rank 2.
Stored as `tl` (weekly) / `day.tl` (daily) in charts.json and `tl_state`, `tl_pattern`, `tl_vol_ratio`, `tl_vol_ok`, `tl_level` (resistance value on the last bar) and `tl_dist_pct` (how many % the price still needs to reach it; > 0 = below) in
watchlist.json ("Trendlinia" column). Drawn as dashed orange (resistance) / grey (support) lines (each with its price at the right end = the level to monitor for a breakout; cups get `pivot <rim price>`), the pole as a thick
translucent segment labelled "maszt +N%", ▲ at a breakout, outlined breakout volume bar; `patternExplain` (chart.js)
turns `info` into a plain-Polish explanation shown in `#chartPattern` under the stats line — the point is to teach the
user to recognise the pattern, so keep the explanation in sync with the criteria above. Daily view is the default
(`momentum_watchlist_chart_daily` = "0" → weekly) with only SMA 10/20 (weekly: SMA 10/40 weeks); the legend lives in
its own band above the price panel so labels never cover candles.

## RS line (chart)

Blue line = stock close / S&P 500 close on the chart's own bars (weekly or daily), drawn in the lower third of the price
panel with its own min–max scale (only shape/direction matter). Meaning comes from the flags, computed in
`rs_line_flags` on the FULL history (not the visible window): `rs_hi` = RS above all of the previous 252 sessions
(52 weeks on the weekly chart), `px_hi` = same for the price. Dot = RS at a 52-week high; **larger white-ringed dot =
RS at a high while the price is not ("RS przed ceną", the leading signal MarketSmith/IBD stress)**. Legend shows the RS
Rating, % change of the ratio over the window ("+72% vs S&P") and the current state. `rs_line_state`
("przed ceną"/"na szczycie" within the last 5 sessions) and `rs_line_dist_pct` (distance from the 52w RS high) feed the
"Linia RS" column. This is NOT the RS Rating (percentile rank among the list, `rs_rating`).
